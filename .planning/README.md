# 短期任务规划目录使用规范 (.planning/)

更新日期：2026-06-04

为了保障 **Werewolf Ville** 在长期迭代中，任务状态不会因为模型上下文重置、长会话断线或 Agent 切换而丢失，项目引入 `.planning/` 目录作为短期/大中型任务的执行追踪机制。

---

## 1. 目录结构

当启动一个非平凡任务（如重构、大 Bug 修复、新玩法开发）时，必须在 `.planning/` 下创建一个以任务简称为名的子目录。例如：
- `.planning/split_navigation/` (拆分导航逻辑)
- `.planning/fix_bubble_logic/` (修复气泡重叠与克罗蓝气泡)

每个任务子目录下必须包含以下三个核心文件：
1. `task_plan.md`（任务方案）
2. `findings.md`（事实发现）
3. `progress.md`（进度与清单）

---

## 2. 三大文件的使用规范

### 2.1 任务方案 `task_plan.md`
*   **用途**：在任务动手前，用于整理思路、设计方案和明确安全边界。
*   **编写时机**：任务启动前。
*   **核心内容**：
    *   **目标与范围**：要修改哪些文件，不修改哪些文件（必须明确写出防污染范围，如 `personas/*` 运行态文件）。
    *   **架构设计**：如果是重构，画出重构后的依赖关系（可使用 Mermaid）。
    *   **步骤分解**：详细的步骤，每步要运行的命令。
    *   **回滚方案**：万一失败如何恢复（如 Git 命令或备份文件恢复）。
*   **示例模板**：
    ```markdown
    # 任务方案：[任务名称]
    
    ## 1. 目标与边界
    - 目标：...
    - 涉及文件：...
    - 禁止修改：`personas/*` 运行态文件，不在此任务范围内的 game_engine.py 部分。
    
    ## 2. 方案设计
    - [设计说明/Mermaid图]
    
    ## 3. 执行步骤
    1. 步骤一：...
    2. 步骤二：...
    
    ## 4. 安全与回滚
    - 备份/Git命令：`git stash` / `git checkout -- <file>`
    ```

### 2.2 事实发现 `findings.md`
*   **用途**：记录在开发、调试或代码阅读中发现的**客观事实**。
*   **编写时机**：执行任务期间，随查随记。
*   **核心内容**：
    *   代码逻辑中的坑（如“发现 `game_engine.py` 第 300 行有硬编码的超时时长”）。
    *   API 契约或 JSON 数据格式（如“Phaser 期望的格式是 `{event: 'x', data: {}}`，但后端发送的是 `{event: 'x', ...}`”）。
    *   测试失败的堆栈和根因分析。
    *   **重要原则**：只记录经过验证的事实，不记录主观猜测；不贴几百行的冗余日志，只贴关键行或精简后的堆栈。
*   **示例模板**：
    ```markdown
    # 事实发现：[任务名称]
    
    ## 1. 代码事实
    - `game_engine.py#L340` 存在循环依赖隐患，调用了...
    
    ## 2. 协议与数据
    - 发现前端 WebSocket 接收格式为...
    
    ## 3. 测试与 Bug 根因
    - 运行 `pytest tests/test_vote.py` 失败，原因是...
    ```

### 2.3 进度与清单 `progress.md`
*   **用途**：任务执行过程中的动态仪表盘，便于任何时候“热启动”恢复上下文。
*   **编写时机**：每个步骤完成时，或每次 turn 结束前更新。
*   **核心内容**：
    *   任务状态（未开始、进行中、已完成、已挂起）。
    *   当前正在做哪一步（Current Focus）。
    *   **检查清单 (Checklist)**：已完成 the check `[x]`，未完成 the check `[ ]`。
    *   验证记录：每次修改后运行了什么测试，浏览器验证结果。
    *   卡点/待办（Blockers / TODOs）。
*   **示例模板**：
    ```markdown
    # 任务进度：[任务名称]
    
    - 状态：进行中
    - 当前焦点：正在抽取 `engine_navigation.py`
    
    ## 进度清单
    - [x] 创建 `engine_navigation.py`
    - [ ] 迁移地图数据函数
    - [ ] 运行静态编译检查
    - [ ] pytest 验证
    - [ ] 浏览器手动验证
    
    ## 验证结果记录
    - 2026-06-04 12:00: py_compile 成功。
    - 2026-06-04 12:05: pytest 失败，正在修复...
    ```

## 3. 任务归档与清理机制

当一个任务完成后，为了避免根目录和规划目录过于臃肿：
1.  **更新总文档**：把该任务产出的稳定结论更新到 `PROJECT_CONTINUITY.md` 或 `DECISIONS.md` 中。
2.  **清空或归档**：
    *   在 Git 提交该任务的最终代码时，同步提交对应的 `.planning/task_name/` 文件夹。
    *   若任务已完全结束并并入主分支，可以在 `.planning/` 下保留其目录作为历史参考，或将其移至 `docs/archive/` 下（如果需要长期保留）。
    *   任何时候，`.planning/` 目录下**处于激活状态（进行中）的子目录不应超过 2 个**，确保开发注意力高度集中。
